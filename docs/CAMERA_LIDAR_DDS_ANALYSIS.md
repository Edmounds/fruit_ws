# 雷达接入后相机深度停流：DDS 数据组播与百兆网口

## 结论

本次故障的工程根因是 **DDS 图像传输策略随网卡状态变化，导致本机图像发布受到雷达百兆网口限制**。
雷达网线接入后，Cyclone DDS 自动选择有线口，并允许通过该接口发送数据组播。
高带宽图像传输受阻，表现为彩色图延迟增大、深度话题停止更新，以及 RGBD 心跳消失。

修复将 DDS 组播限制为参与者发现，图像等用户数据改用单播。
雷达保持上电、网线保持连接，相机深度恢复持续更新。
这不是通过关闭雷达、降低相机分辨率或调整曝光绕开故障。

本文记录 2026-10-15 的实机排查。
结论适用于此次接线、订阅关系和软件配置，不代表完整比赛负载已经验收。

## 1. 为什么一开始像供电问题

相机与电脑、雷达由同一块电池供电。
最初的现象是雷达关闭时相机正常，雷达上电后相机异常。
单看这个现象，供电压降、接地干扰和电磁干扰都有可能。

关键对照是：**雷达保持上电，只拔掉连接电脑的雷达网线，相机就能正常启动并输出深度。**

| 用户现场对照 | 雷达供电 | 雷达网线 | 相机结果 |
| --- | --- | --- | --- |
| 雷达关闭 | 关闭 | 未作为独立变量记录 | 深度正常 |
| 雷达开启并接入电脑 | 开启 | 连接 | 相机异常、深度缺失 |
| 雷达继续开启，仅拔网线 | 开启 | 断开 | 深度恢复 |

这说明雷达上电本身不足以触发故障，网线接入才是关键变量。
仅凭拔网线的结果，还不能完全排除网线引入的电气影响。
随后保持接线不变，仅修改 DDS 配置就恢复深度，进一步将问题定位到软件传输路径。
本次没有进行电池电压波形或电磁兼容测量，因此不对整机供电质量作额外结论。

## 2. USB 相机为什么会受到雷达网口影响

相机连接电脑使用 USB，但相机图像在 ROS 进程之间传输时，还会经过 DDS。
这两段通信不是同一条链路：

```text
D435i
  │ USB 图像采集
  ▼
RealSense 驱动
  │ 相机与感知组件可使用进程内通信
  ├── 感知组件
  │
  └── DDS 跨进程发布
        ├── QR 节点
        ├── 图像预览或录包进程
        └── 诊断订阅进程
```

进程内通信不能保证所有图像订阅都绕过 DDS。
只要存在跨进程订阅，DDS 的接口选择和传输策略仍然会影响系统。
因此，USB 设备成功枚举、ROS 节点成功创建，都不等于图像能够持续发布。

### 2.1 接入网线改变了什么

现场诊断记录到两种不同状态：

| 条件 | DDS 自动选择的接口 | 地址 | 默认组播策略 |
| --- | --- | --- | --- |
| 雷达有线口未建立连接 | `wlo1`，Wi-Fi | `192.168.8.112` | 仅参与者发现使用组播 |
| 雷达有线口建立连接 | `enp89s0`，有线 | `192.168.1.5` | 允许发现及用户数据使用组播 |

未接有线口时，诊断日志为：

```text
selected interfaces: wlo1
presumed flaky multicast, use for SPDP only
```

接入有线口后，诊断日志为：

```text
selected interfaces: enp89s0
presumed robust multicast support, use for everything
```

该行为与本机安装的 Cyclone DDS 配置说明一致。
`AllowMulticast=default` 在 Wi-Fi 上映射为 `spdp`，在有线上映射为 `true`。
允许数据组播不代表每个话题始终使用组播，实际发送路径还取决于订阅者及其地址。

本次接线实际协商为 **100 Mbps 全双工**。
这是现场链路速率，不是根据电脑网卡型号推测的速率。

### 2.2 为什么本机通信也可能堵在物理网口

DDS 跨进程通信不等于共享内存通信。
当 DDS 使用有线接口的数据组播时，即使接收进程也在本机，发送仍可能涉及物理接口和发送队列。
内核的组播本地回送不会自动消除物理发送路径的带宽限制。

在当前本机订阅场景中，改用单播后，目的地址属于本机的数据可由 Linux 本地路由投递。
它不需要把整幅图像先发送给雷达，再从雷达返回。
这也不意味着单播在任何网络中都比组播快。
本次修复的关键是避免本机大图像传输被不必要的物理组播路径限速。

## 3. 带宽计算为何支持这个判断

本次相机配置来自 `src/fruit_perception/config/fruit_perception.yaml`：

| 图像 | 尺寸 | 编码 | 单张有效载荷 |
| --- | --- | --- | ---: |
| 彩色图 | 1280 × 720 | RGB8 | 2,764,800 B |
| 原生深度 | 848 × 480 | Z16 / `16UC1` | 814,080 B |
| 对齐深度 | 1280 × 720 | `16UC1` | 1,843,200 B |

以彩色图为例，按配置目标 30 Hz 计算：

```text
1280 × 720 × 3 × 30 × 8 = 663.552 Mbps
```

**仅原始彩色图就超过百兆链路容量，尚未计入深度和协议开销。**
原生深度和对齐深度若各按 30 Hz 传输，分别需要约 195.379 Mbps 和 442.368 Mbps。
这些数值是各图像流的理论有效载荷，不表示现场所有话题始终同时以 30 Hz 发到网口。

反过来，100 Mbps 链路在完全没有协议开销时，最多承载：

```text
100,000,000 ÷ (1280 × 720 × 3 × 8) ≈ 4.52 张彩色图/秒
```

本次故障复现时，末段彩色图接收率约为 **4.4 Hz**。
它对应约 **97.3 Mbps** 图像有效载荷，接近百兆链路上限。
更早的异常录包按完整接收区间估算，彩色图有效载荷约为 **94.6 Mbps**。
这些是由图像大小和接收频率计算的值，不是抓包得到的网口流量。

修复后，在实际图像订阅进行期间，另取 2 秒读取 `enp89s0` 的 `tx_bytes`。
网口平均发送速率约为 **0.003 Mbps**，链路仍保持 100 Mbps。
同时图像恢复更新，说明恢复不是因为有线链路提速。

## 4. 实机对照方法

两轮对照都保持雷达上电、网线连接。
相机分辨率、曝光、深度滤波和对齐配置不变。
两轮均启动源目录中的 `fruit_perception.launch.py`，区域为 A。
该入口包含相机、感知和 QR 节点，不启动比赛任务或运动控制。

诊断进程同时订阅以下话题：

- `/camera/color/image_raw`
- `/camera/depth/image_rect_raw`
- `/camera/aligned_depth_to_color/image_raw`
- `/fruit_perception/camera/rgbd_heartbeat`

订阅使用 `SensorDataQoS`，记录接收时刻、消息时间戳及深度非零比例。
RGBD 心跳是感知组件收到 RGBD 消息后发布的 `std_msgs/msg/Header`。
它能说明 RGBD 是否到达感知组件，但不代表推理或采摘成功。

| 项目 | 修复前 | 修复后 |
| --- | --- | --- |
| `CYCLONEDDS_URI` | 未设置，采用默认策略 | 显式设置 `AllowMulticast=spdp` |
| 采样时长，包含启动 | 28 秒 | 40 秒 |
| 启动后首次原生深度 | 约第 7.79 秒 | 约第 7.77 秒 |
| 首次原生深度至采样结束的观察时长 | 约 20 秒 | 约 32 秒 |
| 稳态比较窗口 | 末约 10 秒 | 末约 10 秒 |

采样时长不同，因此不能直接用总消息数比较性能。
下面以相同长度的末段窗口比较更新率。
测试未启动 Livox ROS 驱动或 Point-LIO，也未发送底盘或机械臂运动命令。
因此，本次复现不依赖点云处理负载，但也不是完整导航并发负载测试。

## 5. 实际数据对比

### 5.1 末段更新率

按窗口内不同 `header.stamp` 的数量除以约 10 秒计算：

| 指标 | 修复前 | 修复后 |
| --- | ---: | ---: |
| 彩色图 | 4.4 Hz | 13.9 Hz |
| 原生深度 | 0 Hz | 29.7 Hz |
| 对齐深度 | 0 Hz | 14.2 Hz |
| RGBD 心跳 | 0 Hz | 14.1 Hz |

原生深度话题存在重复时间戳消息，不能把消息条数直接当作独立采集帧数。
修复后末段收到 453 条原生深度消息，按不同时间戳统计约为 29.7 Hz，而不是 45.3 Hz。
其余指标也采用相同时间戳去重口径。
这些数值是单次现场采样的近似更新率，不是长期性能保证。

### 5.2 接收延迟

延迟定义为诊断进程接收时的系统时间减去消息时间戳。
它包含驱动、发布、传输和接收调度等影响，不等于纯网络延迟。

| 指标 | 修复前 | 修复后 |
| --- | ---: | ---: |
| 彩色图接收延迟中位数 | 943.9 ms | 58.3 ms |
| 原生深度接收延迟中位数 | 稳态无数据 | 42.1 ms |
| 对齐深度接收延迟中位数 | 稳态无数据 | 53.2 ms |
| RGBD 心跳接收延迟中位数 | 稳态无数据 | 61.9 ms |

数值中位数取自各轮实际收到的全部消息。
修复前的深度只有启动初期数据，不能用其短暂延迟表示稳态性能。
彩色图延迟中位数从 943.9 ms 降至 58.3 ms，约减少 **93.8%**。

### 5.3 故障是停流，不是整幅深度归零

修复前共收到 123 条原生深度消息，其中只有 62 个不同时间戳。
这些消息集中在约第 7.79 至 9.92 秒，之后原生深度不再更新。
第一张深度图约有 **62.6%** 像素非零。
对齐深度和 RGBD 心跳在整轮测试中各只收到 1 条。

因此，本次不是持续收到深度图但所有距离都为零。
它也不是只有网页预览异常，因为直接订阅原始 ROS 话题同样观察到停流。

修复后，原生深度持续更新到采样结束，最后一张约有 **64.0%** 像素非零。
最后一张对齐深度约有 **81.4%** 像素非零。
有效像素比例受场景影响，这些数值不是通用验收阈值。

### 5.4 正常启动入口复测

完成对照后，再使用 `./start_fruit_perception.sh --zone A` 启动感知。
另做 9 秒只读订阅，确认修复也适用于日常入口：

| 话题 | 9 秒内接收消息数 | 最后一张有效深度比例 |
| --- | ---: | ---: |
| 彩色图 | 122 | 不适用 |
| 原生深度 | 400 | 65.1% |
| 对齐深度 | 125 | 80.0% |
| RGBD 心跳 | 124 | 不适用 |

这里展示接收消息数，没有将重复时间戳消息换算为独立采集帧率。

## 6. 为什么深度先消失，彩色图仍然存在

相机的原生深度、对齐深度和 RGBD 输出不是完全独立的端到端系统。
同步、滤波、对齐和发布环节存在处理依赖。
当图像发送受阻时，队列积压或回调等待可能影响后续帧处理。
结果可以是彩色图低速更新，而深度及 RGBD 输出停止。

本次已经验证：

1. 默认配置能够复现停流。
2. 接线不变，仅修改 DDS 策略就恢复出流。
3. 修复后图像订阅期间，物理网口采样发送速率约为 0.003 Mbps。

本次没有采集阻塞时的线程栈或完整 DDS 抓包。
因此，尚不能断言具体堵在 SDK 回调、DDS 写入、发送队列或某一把锁上。
**已定位的是传输策略这一工程根因，不是底层某个函数的唯一阻塞点。**
ROS 原生深度话题停流，也不能单独证明相机硬件停止了曝光或 USB 采集。

## 7. 修复内容与边界

修复提交为 `1730a05`。
`scripts/setup_fruit_runtime.bash` 增加：

```bash
export CYCLONEDDS_URI='<CycloneDDS><Domain Id="any"><General><AllowMulticast>spdp</AllowMulticast></General></Domain></CycloneDDS>'
```

`spdp` 保留 DDS 参与者发现所需的组播。
端点发现和用户数据使用单播。
这与关闭所有组播的 `AllowMulticast=false` 不同。

配置放在统一运行环境中，而不是只放在某一个相机启动脚本中。
这样，加载该环境的感知、任务和桥接进程采用一致策略。
当前脚本会覆盖继承的 `CYCLONEDDS_URI`，定制 DDS 配置时需在统一入口维护。

本次没有修改以下内容：

- 相机曝光、增益、分辨率、同步或深度滤波配置。
- RealSense SDK 和驱动实现。
- 雷达 IP、网口速率及 Livox 协议参数。
- 机械臂标定、预设和运动控制接口。

Livox 自身的 UDP 通信不由 `CYCLONEDDS_URI` 控制。
但跨进程发布的雷达 ROS 话题同样会受 DDS 策略影响，完整导航负载仍需单独验证。

修复也不会把百兆网口变成千兆网口。
若远端电脑订阅原始图像，单播仍受物理带宽限制，应使用压缩预览或独立高速链路。
本次 RGB 和对齐深度恢复至约 14 Hz，不代表已经达到配置目标 30 Hz。
短时采样通过也不代表长期运行、录包与完整任务并发已全部验收。

## 8. 现场检查方法

先停止比赛任务，确保底盘和机械臂静止。
保持雷达上电和网线连接，只启动感知。
已运行的 ROS 进程不会自动应用新的环境变量，必须在安全停止后重新启动。

```bash
cd /home/rc4/fruit_ws
source scripts/setup_fruit_runtime.bash
echo "$CYCLONEDDS_URI"
./start_fruit_perception.sh --zone A
```

在另一个已加载运行环境的终端检查链路和出流：

```bash
ip -br address
head -n 1 /sys/class/net/enp89s0/speed
timeout --kill-after=1s 9s ros2 topic hz /camera/depth/image_rect_raw
timeout --kill-after=1s 9s ros2 topic hz /camera/aligned_depth_to_color/image_raw
timeout --kill-after=1s 9s ros2 topic hz /fruit_perception/camera/rgbd_heartbeat
```

`timeout` 到期返回非零状态属于预期行为。
`ros2 topic hz` 统计接收消息，不做时间戳去重，不能直接与本文原生深度帧率比较。
还需检查消息时间戳是否持续前进，以及数值深度是否有非零像素。
不要用 JPEG 深度预览替代数值深度检查，也不要只凭节点列表判断成功。
